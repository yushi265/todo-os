# TODO整理

## 目的

プロジェクトのTODOファイルを、実装状況に基づいて正確かつ読みやすいバックログへ整理する。既定の対象はリポジトリ直下の`TODO.md`とする。ユーザーが別のファイルを指定した場合はそのファイルを対象にする。

## 実行手順

1. リポジトリの入口ルール（`AGENTS.md`、`CLAUDE.md`など）と対象TODOファイルを読む。
2. `git status --short`で既存の変更を確認し、TODO整理と無関係な変更を保持する。
3. TODO各項目に対応する実装・仕様・テストを`rg`などで調査する。現行コードで完了が確認できない項目は、推測でチェックしない。
4. 完了済み項目には`[x]`を付ける。部分完了の場合は、完了部分を独立項目として`[x]`にし、残作業は`[ ]`として具体化する。
5. 未完了項目を優先度別に分類し、`## 未完了`の配下を見出し3（`###`）の`優先度未設定`、`高`、`中`、`低`に分ける。見出しの順序は`優先度未設定 → 高 → 中 → 低`とする。各見出し内では、利用者への効果、依存関係、実装着手のしやすさを基準に並べる。
6. 曖昧な項目は、既存の意図を保ったまま観測可能な作業へ言い換える。新しい要件を勝手に追加しない。
7. 空の項目、重複項目、完了済み項目を未完了欄に残さない。
8. 未完了項目は`## 未完了`の配下で優先度別の見出し3に分け、完了済み項目は`## 完了`に分ける。優先度は項目の末尾に付けず、見出しで表現する。優先度を判定できない項目は先頭の`### 優先度未設定`に置く。新規に追加するTODOで優先度が未定のものも、この見出しへ追加する。

## 表記規則

- 未完了: `- [ ] 内容`
- 完了: `- [x] 内容`
- 未完了の見出しは次の構造にする。
  - `## 未完了`
    - `### 優先度未設定`
    - `### 高`
    - `### 中`
    - `### 低`
- 優先度は項目の末尾に括弧書きせず、「高」「中」「低」「未設定」の見出しで表現する。
- 完了項目も元の目的が分かる文にし、単に「完了」とだけ書き換えない。
- TODOファイル内に既存の案内文・specへのリンク・プロジェクト固有の注記がある場合は保持する。

## 優先度の判定基準

- **高**: 日常の主要操作、データ入力、認証・安全性、他の作業をブロックする基盤に関わるもの。
- **中**: 利用頻度の高いUX改善、検索・分類・発見性の向上、複数画面に影響するが緊急ではないもの。
- **低**: 見た目の磨き込み、将来の選択肢、導入効果が未確認のライブラリ置換、テーマや好みに関するもの。

## 完了判定の証拠

- UI項目は、対象コンポーネント・関連テスト・必要なら仕様書を確認する。
- APIやデータ連携項目は、エンドポイント、呼び出し元、テスト、認証境界を確認する。
- 「似た機能がある」だけでは完了にしない。TODOの要求を満たしている範囲が明確な場合だけ、部分完了として分割する。
- 完了判定に不確実性が残る場合はチェックを付けず、TODO本文に確認事項を残す。

## 更新範囲と検証

- ユーザーがTODO整理だけを依頼した場合、変更対象はTODOファイルだけに限定する。
- 実装、spec作成、コミット、ブランチ操作は依頼されていない限り行わない。
- 更新後に対象ファイルを読み直し、未完了項目が優先度別の見出し配下にあること、項目の末尾に優先度表記がないこと、チェック状態と本文が一致していること、空項目がないことを確認する。
- `git diff --check`を実行し、無関係なファイルを変更していないことを報告する。
