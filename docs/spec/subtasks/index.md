# subtasks: TODO のサブタスク管理

## 概要

TODO 編集画面から、親 TODO に紐づくサブタスクを追加・完了・削除できるようにする。
サブタスクは専用テーブルで管理し、親 TODO の一覧カードには完了数と総数を表示する。

## 対象範囲

- 対象レイヤー: service（Drizzle/D1 を含む）・ui（React）
  - [service.md](./service.md)
  - [ui.md](./ui.md)
- 対象ドメイン: TODO / サブタスク
- 対象外:
  - サブタスクの中にさらにサブタスクを作る多重階層
  - サブタスクの手動並び替え
  - サブタスクへの優先度・期限・タグ・説明の付与
  - サブタスクを通常の TODO 一覧へ独立した行として表示すること

## ユニット計画

単一ユニットで完結する。

## 受け入れ基準（AC）

- [ ] **AC-1**: 既存 TODO の編集画面で、タイトル（1〜200文字必須）を指定してサブタスクを追加できる。追加したサブタスクは親 TODO に紐づいて保存され、通常の TODO 一覧には独立した行として表示されない
- [ ] **AC-2**: 親 TODO の取得レスポンスには、紐づくサブタスクが作成順で含まれる。TODO 一覧カードにはサブタスクの完了数/総数を表示する
- [ ] **AC-3**: 編集画面でサブタスクの完了状態を切り替えられ、変更が保存される。完了数/総数の表示も更新される
- [ ] **AC-4**: 編集画面でサブタスクを削除できる。親 TODO を削除した場合は、紐づくサブタスクも削除される
- [ ] **AC-5**: サブタスクのタイトルが空文字または201文字以上の場合、追加は400エラーとなり、既存データは変更されない。完了状態以外の不正な更新値も400エラーとなる
- [ ] **AC-6**: 存在しない親 TODO、存在しないサブタスク、または別の親に属するサブタスクへの操作は404エラーとなる
- [ ] **AC-7**: 既存 TODO の作成・取得・更新・削除・タグ・並び替えの挙動は、サブタスク未使用時も従来どおり維持される

## アーキテクチャ / レイヤー間フロー

```text
ui（TodoFormModal / TodoSubtaskList）
  │ fetch /api/todos/:todoId/subtasks...
  ▼
service（Hono + Zod）
  │ Drizzle ORM
  ▼
D1（subtasks。todo_id → todos.id、ON DELETE CASCADE）
```

サブタスクは `todos` テーブルの自己参照ではなく専用テーブルで管理する。通常の TODO 一覧は既存の `todos` のみを取得し、レスポンス構築時にサブタスクを一括取得して親 TODO に付与する。

## エラー・ログ方針（横断サマリ）

| シナリオ | service | ui の挙動 |
|---|---|---|
| サブタスクのタイトル不正 | 400 `{ error: "Validation failed", details }` | 入力欄の下にエラーを表示し、送信を維持 |
| 存在しない親/サブタスク、親子関係不一致 | 404 `{ error: "Todo not found" }` または `{ error: "Subtask not found" }` | 「サブタスクが見つかりませんでした」を表示し、親のサブタスクを再取得 |
| D1 障害・想定外エラー | 500 `{ error: "Internal server error" }` | 「時間をおいて再度お試しください」を表示 |

想定外エラーは既存の `app.onError` でログ出力し、レスポンスには内部詳細を含めない。

| AC-1 | スキーマ境界値 | POST /api/todos/:id/subtasks、編集画面 |

| AC-3 | — | PATCH /api/todos/:id/subtasks/:subtaskId、編集画面 |
| AC-4 | — | DELETE API、親削除のカスケード、編集画面 |

## 既存実装との関係（再利用 / 差分 / 衝突）

- 再利用: `src/worker/routes/todos.ts` の親 TODO 検索、`parseJsonBody`、`ErrorResponse`、`requestJson`/`requestVoid`、`ModalFrame`、既存の TanStack Query キャッシュ無効化パターンを使う。
- 差分: `src/db/schema.ts` に `subtasks` テーブル、`src/shared/schemas.ts`/`types.ts` にサブタスク契約、API にネストした CRUD、UI にサブタスク管理欄と進捗表示を追加する。
- 衝突回避: 既存の `TodoResponse` のタグ・並び替え・フィルター契約は維持し、サブタスクは `subtasks` フィールドとして追加する。

## 実装に効く制約

- 親 TODO は通常の `todos` レコードであり、サブタスクは通常一覧の取得対象から除外する。
- サブタスクの並びは `id` 昇順（作成順）で固定する。
- 既存 API のレスポンスに `subtasks: []` を常に含め、未使用時も契約を安定させる。
- 親削除とサブタスク削除は D1 の外部キー `ON DELETE CASCADE` で担保する。
- UI の入力ルールは service と共有する Zod スキーマで検証する。

## 判断根拠 / 未決事項

- 専用テーブルを採用した。サブタスク固有の完了状態を親 TODO のステータスと混同せず、親削除時のカスケードをDB制約で単純に担保できるため。`todos` の自己参照は通常一覧・並び替え・フィルターの除外条件を増やすため採用しない。
- API は既存 TODO API のネストしたパスにする。サブタスクが親の境界を越えて操作されないことをパスとクエリで検証でき、UI の責務も分かりやすいため。
- 編集画面の初期データは `GET /api/todos/:todoId/subtasks` で取得する。一覧レスポンスにもサブタスク概要を含め、一覧カードの進捗表示と編集画面の最新データ取得を両立する。
- 未決事項はない（ユーザー確認済み: 1階層、タイトル/完了状態、編集画面で管理、進捗表示、親削除時の連動削除、一覧では独立表示しない）。
