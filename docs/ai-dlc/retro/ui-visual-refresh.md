## 振り返り（KPT）

### Keep（効いた・次も続ける）
- worklogチェックポイント運用が、3回のAPI中断（うち2回は実装委譲）を無損失で乗り切る決め手になった。中断のたびに`git status`/`pnpm test`で実物確認してから再開させる運用が機能した
- 3体並列レビュー + オーケストレーター監査（Must指摘の実物裏取り・抜き取り検査）が、実装エージェントの完了報告だけでは見えない欠落（AC-4の統合テスト欠落）を確実に捕捉した
- オーケストレーター自身が実装コード（`handleAdvanceStatus`）を読んで検証したことで、3体のレビューにも出てこなかった追加のテストギャップ（異常系「その他エラー」の未テスト）を発見できた

### Problem（詰まった・摩擦・想定外）
- `[tooling]` 実装委譲中にAPIエラー（マシンスリープ・セッション上限）による中断が3回発生した。worklogのおかげで実害は無かったが、頻度として無視できない水準だった
- `[spec]` 異常系挙動表に書いたシナリオ（「ステータス進行PATCHがその他エラー」の行）がテストケース節への転記から漏れた。これは`tag-management`のretro noteで既に指摘済みの学び（learnings.md「異常系挙動表の全シナリオをテストケース節にも転記する」）が、正式ルールへ未昇格のまま今回のユニットでも再発したことを示す
- `[review]` Gate2承認時点のspec（ui.md）に、実装時に初めて確定する視覚的な詳細（トースト背景色・`CompletedToggle`のシャドウ値・`TagMultiSelect`のチップ配色マッピング・`updatedAt`の表示フォーマット）が書き切れておらず、self-reviewでSpec-conformance-reviewerからShould指摘として複数件検出された。大規模なビジュアル刷新specの宿命だが、Gate2時点の網羅性には限界があった

### Try（次ボルト以降でフローをこう変える）
- `learnings.md`の「異常系挙動表→テストケース節への転記漏れ」エントリが2ユニット連続（tag-management, ui-visual-refresh）で再発している。次回の`retro-triage`実施時にこれを最優先で正式ルール昇格（`.claude/skills/create-spec/SKILL.md`への明記、または機械チェック可能な sensor 化）の対象にする
- ビジュアル刷新系のspecでは「実装時に確定する視覚的な微細値（影・背景色トークンの転用等）は実装完了後にspecへ書き戻す」ことを前提にし、Gate2の完全性ではなくGate3前のspec同期チェックとして運用する方が実態に合う
